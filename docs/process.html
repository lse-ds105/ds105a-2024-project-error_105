Pokemon Data

Pokémon Data Collection

This section details the methodology for retrieving and processing Pokémon data from the PokeAPI. The approach ensures efficient data collection, structuring, and storage while utilizing parallel processing techniques to optimize performance.

Asynchronous API Requests with ThreadPoolExecutor

There are 1025 different Pokémon, so we explored efficient ways to collect data regarding each individual Pokémon. The requests library is used to query the PokeAPI for data on all Pokémon species. The ThreadPoolExecutor module enables concurrent API calls, significantly reducing execution time.

  • The collected data is structured into Pandas DataFrames and saved as JSON files for further analysis.
  • Through parallel execution, the time to collect the data was reduced by a factor of 10.

Extracting and Organizing Pokémon Identifiers

Each Pokémon was identified by querying data from every generation, from Generation I to Generation IX. The Pokémon’s ID was extracted from the collected URL and assigned to a new column in the dataframe.

Comprehensive Data Collection for Each Pokémon

The data for each Pokémon was collected in two steps:

  • Pokemon-specific Details: Extracts fundamental attributes such as name, base stats, and sprite images. Non-essential data is removed, and the required data is stored in a JSON structure.
  • Species Details: Retrieves species-specific information, including Pokédex flavor text. Filters and retains only the first available English descriptions for clarity.

Error Handling

Any API request failures or missing data points are logged and managed to prevent script interruptions. It was reflected that data was successfully collected for all 1025 Pokémon.

Pokémon Data Processing

Data Extraction and Transformation

Data was collected and processed from the JSON format into a Pandas DataFrame using the following steps:

  • Loading Data: Utilized the JSON and Pandas libraries to read and load Pokémon data from JSON files into DataFrames.
  • Normalization: Applied pd.json_normalize to flatten nested JSON structures, making it easier to manipulate the data.
  • Data Integration: Merged various data sources into a comprehensive DataFrame containing attributes like habitat, description, types, and statistical metrics.

Statistical Calculations

Statistical calculations were executed to compute aggregate statistics for each Pokémon, facilitating ranking and comparison.

  • Total Stat Calculation: Summed individual stats (HP, attack, defense, special attack, special defense, speed) to derive a total_stat metric for each Pokémon.
  • Ranking: Sorted Pokémon based on their total_stat, with tiebreakers based on HP stat to reflect their ability to tolerate intense climates.

Dominant Colour Extraction from Images

The dominant color of each Pokémon's image was determined using the following process:

  • Image Retrieval: Downloaded Pokémon images using URLs provided in the dataset.
  • Background Removal: Filtered out black and white pixels to focus on the Pokémon's primary colors.
  • Colour Clustering: Employed the K-Means clustering algorithm to identify the dominant RGB color in each image.
  • Colour Classification: Converted RGB values to HSV to classify colors into categories like red, orange, yellow, etc.

Data Storage and Accessibility

Processed Pokémon data was stored in structured formats for future analysis and application development:

  • JSON Export: The main Pokémon DataFrame was saved as a JSON file for easy sharing and future use.
  • Database Integration: Utilized SQLite to create separate tables for fire, ice, and water type Pokémon, storing relevant attributes and rankings.

Storing the data in both JSON and database formats ensures flexibility, allowing for efficient querying and integration with other applications or analyses. The SQL tables will be utilized for the integration of the different forms of data.

Considerations and Challenges

  • Image Processing Limitation: Encountered an issue with Pokémon ID 678, whose image could not be processed due to a bug. Assigned a manual RGB value to address this.
  • Background Removal Impact: The background removal process eliminated all white pixels, resulting in no Pokémon being classified with white as their dominant colour.
  • Concurrency Warning: Despite setting the 'OMP_NUM_THREADS' to 1, a UserWarning regarding thread settings persisted during K-Means clustering.

Biome Data

Biome Data Collection

This section focuses on collecting and analyzing biome data by determining the center coordinates of each ecoregion for the 14 biomes present in the Ecoregions 2017 Resolve dataset from Google Earth Engine (GEE). By identifying the central coordinates, we can use these coordinates to find out more data (e.g., weather data) using other APIs.

Use of a Service Account to Authenticate Google Earth Engine

Google Earth Engine (GEE) requires authentication to access its resources. While manual authentication (OAuth) is fine for interactive use, a service account is the best option for automated data collection.

  • What is a Service Account: A service account is a special type of Google account designed for applications rather than individuals. It allows scripts and automated workflows to authenticate with Google services securely, without requiring manual login.
  • Why Use a Service Account for GEE:
    • Automation & Batch Processing: A service account enables scripts to run unattended, making it ideal for processing large datasets in Google Earth Engine.
    • Security: Unlike personal accounts, service accounts use private keys for authentication, ensuring secure access control.
    • Cloud Integration: Essential for running scripts on Google Colab, Google Cloud, or other remote servers without needing user interaction.
    • Team Collaboration: Service accounts allow multiple team members to access shared resources without compromising personal credentials.

By using a service account, the biome data extraction process can run automatically, reducing manual intervention and improving efficiency.

Rationale for Using .py Script to Collect and Process Data for Biomes

A Python script was used to collect and process the biome data due to the following advantages:

  • Batch Processing for Efficiency: Given the large dataset, biome data was collected in batches to optimize runtime and prevent exceeding computational limits.
  • Automated Data Extraction: The script leverages Google Earth Engine’s Python API to fetch relevant biome data efficiently.
  • Custom Filtering & Processing: The script applies filters to extract only the required information (e.g., center coordinates, biome types, ecoregions) as the huge amount of raw data makes it impractical to be collected.

Weather Data

Weather Data Collection

This section focuses on collecting and analysing the data from open-meteo to identify the hottest, coldest, and rainiest locations in the world, and visualise any trends encountered along the way.

Weather Data Collection

This section aims to identify and rank geographical locations based on climatic extremes (hottest, coldest, and wettest regions) while evaluating their spatial patterns and exploring their potential influence on Pokémon distribution.

  • Use of asyncio for Asynchronous Requests: The asyncio library was implemented to efficiently handle API calls, enabling the retrieval of large volumes of forecasted weather data in parallel.
  • Significance: This asynchronous approach significantly reduced the runtime of data collection, allowing the analysis to handle real-time, high-frequency data from diverse geographical regions.
  • Scalability: By employing asyncio, the script demonstrates scalability and efficiency, ensuring that data for thousands of global centroids can be processed rapidly and without unnecessary delays.

Rationale for Using Forecasted Data

The decision to use forecasted weather data, rather than purely historical datasets, was motivated by a desire to evaluate how Pokémon might adapt and move across varying climatic conditions in the near future.

Weather Data Processing

Climatic rankings and analysis were performed to assess the hottest, coldest, and wettest places globally. Additionally, exploratory mapping with Folium and geographical regression were used to visualize and analyze spatial and temporal variations in climate extremes.

Integration

During the data exploration process, we realized that the API did not collect data on every Pokémon’s habitat. As such, the integration was done based on ranking Pokémon by their stat totals, with tiebreakers resolved by their health points.

The final dataset was integrated using SQL tables, joining Pokémon data with weather data and biomes. This allowed us to create an interactive map with Pokémon locations and weather trends.

Visualisation

Using the tables created, an interactive map was created with the following features:

  • Heatmap: Displaying the hottest, coldest, and wettest places globally.
  • Fire Pokémon: Layer containing the locations of all fire-type Pokémon.
  • Ice Pokémon: Layer containing the locations of all ice-type Pokémon.
  • Water Pokémon: Layer containing the locations of all water-type Pokémon.

The map is scrollable and zoomable for detailed exploration. It also includes a search bar to easily locate specific Pokémon.
